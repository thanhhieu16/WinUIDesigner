# Phase 4f: PropertyGrid — Design Spec

## Context

Phase 4e ("Metadata") shipped a static registry (`src/WinUIDesigner.DesignModel/Metadata.cs`) with `IsBrowsable`, `IsPopularProperty`, `GetStandardValues` (×2 overloads), `GetNamedStandardValues`, `GetValueRange`, `GetDefaultSize`, `GetDefaultPropertyValues` — all built with **zero production callers**, explicitly to give Phase 4f (PropertyGrid) and Phase 5 (Toolbox) their first real consumers (Phase 4e spec Decision 7). `IComponentPropertyService` (property enumeration by reflection) was ported even earlier, in Phase 2, and is likewise unconsumed until now (`src/WinUIDesigner.DesignModel/Services.cs:43-48`, impl at `src/WinUIDesigner.DesignModel/Xaml/XamlDesignContext.cs:119-154`).

Phase 4f builds the design-time property-editing UI panel that consumes all of the above: a control that, given a selection of `DesignItem`s, lists their editable properties grouped into categories, and lets the user edit values with undo support.

Original scope note (Phase 2 spec, `docs/superpowers/specs/2026-09-01-winui-designmodel-phase2-design.md:346`): "property grid, metadata, and outline view" were named as one deferred Phase 4 item; that item was split into 4e (Metadata, done) → 4f (PropertyGrid, this spec) → 4g (OutlineView, not started) per this project's own later decomposition.

Repo state: confirmed greenfield — zero matches for `PropertyGrid`/`PropertyNode`/`PropertyEditor` anywhere in `src/`/`tests/`.

## Verified against the current codebase

- **Zero `.xaml` files exist anywhere in `src/`** (confirmed via `find src -name "*.xaml"`, 0 results). Every prior phase's visuals (adorners, thumbs, snaplines, context menus) are built via plain C# object construction — confirmed in `src/WinUIDesigner.Designer/Controls/GridAdorner.cs`, `src/WinUIDesigner.Designer/Extensions/SnaplinePlacementBehavior.cs`, `RasterPlacementBehavior.cs`, `StackPanelPlacementSupport.cs`, `GridUnitSelector.cs`, `GrayOutDesignerExceptActiveArea.cs`. This resolves the reference's WPF-implicit-`DataTemplate`-by-`DataType` rendering mechanism (`PropertyGridView.xaml:123,141`) as **not applicable** — this port builds category/property rows the same way every other visual in this codebase is built: C# factory methods, not markup, not a `DataTemplateSelector`.
- **`DependencyPropertyDescriptor` has no WinUI equivalent**, already flagged at `src/WinUIDesigner.XamlDom/XamlParser.cs:549-554`. Reference's `PropertyNode.Name` (`PropertyNode.cs:50-67`) and `PropertyGrid.PickCategory`'s attached-property branch (`PropertyGrid.cs:308`, via `IsAttachedDependencyProperty()`) both depend on it. Substitute: `WinUIDesigner.XamlDom.XamlProperty.IsAttached`/`.PropertyTargetType` already exist and are already consumed at `src/WinUIDesigner.DesignModel/Xaml/XamlDesignItem.cs:165-166` — but `DesignItemProperty` (the abstract base every layer above `XamlModelProperty` programs against) has no equivalent member (confirmed by reading `src/WinUIDesigner.DesignModel/DesignItemProperty.cs:27-80` in full — no `IsAttached`-shaped member exists). This phase adds one (Decision 1).
- **`DesignItemProperty.DeclaringType`** (abstract, `DesignItemProperty.cs:31`) is implemented by `XamlModelProperty.DeclaringType` (`src/WinUIDesigner.DesignModel/Xaml/XamlModelProperty.cs:100-102`) as `_property.PropertyTargetType` — for an attached property this is already the *owner* type (e.g. `Grid` for `Grid.Row`), matching what a qualified display name needs, with no extra plumbing required beyond exposing attached-ness itself.
- **`DesignItemProperty.FullName`** (`DesignItemProperty.cs:56-58`, `DeclaringType.FullName + "." + Name`) is correct and already used as `Metadata`'s lookup key (Phase 4e). **`DependencyFullName`/`DependencyPropertyExtensions.GetFullName`** (`DesignItemProperty.cs:64-71,98-107`) remain confirmed broken (Phase 4e finding) — this phase must not call either.
- **Property enumeration**: `DesignItem.Properties`/`AllSetProperties` (`src/WinUIDesigner.DesignModel/DesignItem.cs:87,92`) only cover properties already materialized/already set in the XAML source (confirmed via `src/WinUIDesigner.DesignModel/Xaml/XamlModelPropertyCollection.cs:28-60` — `GetEnumerator` yields only previously-`GetProperty`'d entries). The full CLR property surface comes from `IComponentPropertyService.GetAvailableProperties`/`GetCommonAvailableProperties` (`Services.cs:43-48`), implemented at `XamlDesignContext.cs:119-154` via `System.ComponentModel.TypeDescriptor.GetProperties(designItem.Component)` against the live component instance — already registered into every `XamlDesignContext` at construction (`XamlDesignContext.cs:50`).
- **Undo**: `XamlModelProperty.SetValue`/`Reset` (`src/WinUIDesigner.DesignModel/Xaml/XamlModelProperty.cs:220-259`) already route through `UndoService.Execute(new PropertyChangeAction(...))` with no `ChangeGroup` needed for a single edit. `UndoService` is registered for every `XamlDesignContext` at construction (`XamlDesignContext.cs:51`), so this works with no shell app present.
- **`ISelectionService`** is only auto-registered by `DesignSurface.LoadDesigner` (`src/WinUIDesigner.Designer/DesignSurface.cs:35`), not by a bare `XamlDesignContext`. Tests using a bare context register it manually via `CustomServiceRegisterFunctions`, the same pattern already established in `ModelToolsTests.cs`/`CreateComponentToolTests.cs`.
- **`EditorManager.CreateEditor`** (`F:\...\EditorManager.cs:46-101`) has a genuine dead-code bug in the reference: after its base-type-walk loop (lines 51-56) finds and `break`s with a match, execution falls through unconditionally into a second `foreach (var t in typeEditors) if (t.Key.IsAssignableFrom(...)) return ...` (lines 58-62) that ignores the walk's result entirely — whichever registered type is enumerated first and is assignable wins, not necessarily the walked match. This is not reproduced (Decision 4).
- **`Category.cs`** (95 lines) is a plain view-model; its `Properties` collection is a custom `PropertyNodeCollection` (`SortedObservableCollection`-based) that inserts pre-sorted. Reference's own `PropertyGrid.UpdateChildren`-equivalent (`PropertyNode.cs:412-438`) already does `.OrderBy(d => d.Name)` once before construction — a full rebuild-and-resort on every reload makes a live-sorted-insert collection unnecessary (Decision 5).
- **`IPropertyDescriptionService`** (consumed by reference `PropertyNode.Description`, `PropertyNode.cs:145-153`) does not exist anywhere in this port (confirmed via repo-wide grep, 0 matches) — dropped cleanly, nothing depends on it.
- **Existing attached-property XAML test fixture pattern** already exists: `tests/WinUIDesigner.Designer.Tests/GridAdornerProviderTests.cs:28,45` load `Grid.Row="1"`/`Grid.RowSpan="2"` on a child `Button` inside a `Grid` — this phase's `IsAttachedProperty` tests reuse the same fixture shape.
- **`NumberBox`, `ComboBox`, `CheckBox`, `TextBox`** (`Microsoft.UI.Xaml.Controls`) are assumed available and stable WinUI 3 controls with the properties this phase needs (`NumberBox.Minimum/Maximum/Value`, `ComboBox.ItemsSource/SelectedValue/DisplayMemberPath/SelectedValuePath`, `CheckBox.IsChecked`, `TextBox.Text`) — **not yet empirically probed in this codebase**; the first task touching each should confirm via a real build+test, not assume (flagged in Known gaps, not blocking the design).

## Decisions already made

1. **New `DesignItemProperty.IsAttachedProperty` virtual member** (`src/WinUIDesigner.DesignModel/DesignItemProperty.cs`), default `false`; overridden by `XamlModelProperty` (`src/WinUIDesigner.DesignModel/Xaml/XamlModelProperty.cs`) to return the wrapped `XamlProperty.IsAttached`. Needed for both `PickCategory`'s Attached bucket and display-name qualification — replaces the reference's `DependencyPropertyDescriptor`-based detection with data this port already computes elsewhere. This is the one change to already-shipped foundational code this phase makes (matches the brainstorming skill's "targeted improvements to existing code that serves the current goal" guidance).
2. **Attached-property display name**: `IsAttachedProperty ? DeclaringType.Name + "." + Name : Name` — no `DependencyPropertyDescriptor` needed; `DeclaringType` already resolves to the owner type for an attached property (verified above).
3. **Two-project split, mirroring every prior phase**: `src/WinUIDesigner.DesignModel/PropertyGrid/` (`PropertyNode.cs`, `Category.cs`, `EditorManager.cs` — no WinUI-Controls-specific dependency) and `src/WinUIDesigner.Designer/PropertyGrid/` (`PropertyGridControl.cs` + `Editors/`). `WinUIDesigner.DesignModel` must not reference `WinUIDesigner.Designer` (existing `ProjectReference` direction, unchanged).
4. **`EditorManager` registration is delegate-based, not `Type`+`Activator.CreateInstance`-based**: `RegisterTypeEditor(Type clrType, Func<DesignItemProperty, FrameworkElement> factory)`, `SetDefaultComboBoxEditorFactory(Func<DesignItemProperty, FrameworkElement>)`, `SetDefaultTextBoxEditorFactory(Func<DesignItemProperty, FrameworkElement>)`. Simpler than the reference's reflection+attribute-scanning (`RegisterAssembly`/`[TypeEditorAttribute]`/`[PropertyEditorAttribute]`, none of which are ported — see Decision 8), avoids the reference's dead-branch bug (no separate walk-then-rescan step), and keeps `WinUIDesigner.Designer` (owner of the concrete editor classes) decoupled from `WinUIDesigner.DesignModel` (owner of `EditorManager`) via a one-time registration call the Designer layer makes, not a project reference. Each editor class is responsible for registering itself (mirroring the reference's own decentralized `[TypeEditorAttribute]`-on-itself pattern, just via a static method call instead of an attribute): `NumberEditor` registers all of `byte/sbyte/short/ushort/int/uint/long/ulong/float/double/decimal` plus their nullable variants (each its own exact dictionary entry — no base-type walking needed, since Phase 4f's fixed editor set has no derived-type polymorphism to resolve) against itself; `BoolEditor` registers `bool`/`bool?`; `ComboBoxEditor` and `TextBoxEditor` register themselves as the two *default* factories, not exact-type entries. `PropertyGridControl`'s static constructor calls each of the four editors' `Register()` once, before any `EditorManager.CreateEditor` call can occur. `CreateEditor(DesignItemProperty property)` resolution order: (a) exact `property.ReturnType` match in the registered dictionary; (b) `Metadata.GetStandardValues(property.DependencyProperty)` then `Metadata.GetStandardValues(property.ReturnType)` (this already internally special-cases every enum type — confirmed in `Metadata.cs`'s Phase 4e implementation, no separate enum branch needed here) → default combo-box factory; (c) `Metadata.GetNamedStandardValues(property.ReturnType)` → default combo-box factory (named variant); (d) default textbox factory.
5. **No `PropertyNodeCollection`/`SortedObservableCollection` port**: `Category.Properties` is a plain `IReadOnlyList<PropertyNode>`, built once per reload via `.OrderBy(n => n.Name)` — matches the reference's own already-sorted construction pattern, just without a live-resorting collection type nobody needs (full rebuild happens on every `Reload()` regardless).
6. **`PropertyGrid.cs`'s controller logic folds directly into `PropertyGridControl`** — no separate non-visual `IPropertyGrid`/`PropertyGrid` class distinct from the `Control`. Reference splits them because WPF data-binds a XAML view to a separate view-model; this port has no XAML view layer to bind (Decision "Zero `.xaml` files" above), so the split has no purpose here. `PropertyGridControl` owns: 4 fixed `Category` instances (Special/Popular/Other/Attached), `SelectedItems` (settable `ICollection<DesignItem>`, drives `Reload()`), a `Dictionary<string, PropertyNode>` node cache keyed by property name (not `MemberDescriptor` identity — string-keyed, matching the project-wide `DesignItemProperty`/`Metadata` convention), and the visual tree built via C# factory methods (`BuildCategoryRow`/`BuildPropertyRow`).
7. **`PickCategory` bucketing**, ported with one simplified namespace check: `Metadata.IsPopularProperty(node.FirstProperty)` → Popular; else `node.FirstProperty.IsAttachedProperty` → Attached; else `DeclaringType.FullName.StartsWith("Microsoft.UI.Xaml.")` → Other; else → Special. (Reference checks two namespace prefixes — its own WPF namespace plus its own custom-controls namespace; this port has no equivalent second namespace a user-selectable control would ever belong to, so one prefix suffices.)
8. **No `[PropertyEditorAttribute]`/`[TypeEditorAttribute]`/`EditorManager.RegisterAssembly` reflection-scanning mechanism ported.** Nothing registers a custom per-property or third-party-type editor override in this codebase yet, and the fixed 4-editor MVP set needs no such extensibility seam. `RegisterTypeEditor`/`SetDefault*Factory` (Decision 4) remain the only registration surface; if a future phase needs attribute-driven overrides, that is new work then, not a seam left dangling now (unlike `Metadata`'s Phase 4e mechanism-only methods, this is a deliberate YAGNI cut, not a deferred-with-seam).
9. **Editor set for this phase**: `BoolEditor` (`bool`/`bool?` → `CheckBox`), `ComboBoxEditor` (default combo factory, used for both standard-values and named-standard-values resolution paths — enum types included automatically via `Metadata.GetStandardValues`'s existing enum handling), `NumberEditor` (`byte/sbyte/short/ushort/int/uint/long/ulong/float/double/decimal` and their nullable variants, each registered as its own exact entry, → `NumberBox` consuming `Metadata.GetValueRange` for `Minimum`/`Maximum` when registered, else the CLR type's own min/max), `TextBoxEditor` (default textbox factory, the fallback for everything else — `string`, and any type with a working `TypeConverter` round-trip via `ConvertFromInvariantString`/`ConvertToInvariantString`). Brush/Color/Collection/TimeSpan/Event/RichText editors are explicitly deferred (unregistered types fall through to `TextBoxEditor`).
10. **Multi-select is in scope from the start** (not a later addition): `PropertyNode.Properties` is `DesignItemProperty[]` (one per selected `DesignItem` sharing the property name), `IsAmbiguous` ported as-is (`PropertyNode.cs:266-275` pattern: any property whose `ValueOnInstance` differs from `FirstProperty`'s). `IComponentPropertyService.GetCommonAvailableProperties` (already ported, Phase 2) is the multi-select descriptor source; `GetAvailableProperties` is the single-select source.
11. **Recursive complex-property drill-down is in scope**: `PropertyNode.Children`/`MoreChildren`, built lazily on `IsExpanded`, for any property whose value is itself a `DesignItem`-tracked object (`ValueItem != null`) — bucketed via the same `Metadata.IsPopularProperty`/`IsBrowsable` calls used at the root level (`PropertyNode.cs:412-438` pattern). Not gated on having a dedicated editor for the sub-object's own type; the sub-object's own scalar properties (e.g. `RotateTransform.Angle`) are editable via the same 4 MVP editors.
12. **`PropertyNode.SetValueCore`'s `TextBlock.Text`-vs-`Inlines`-collection special case is not ported** (`PropertyNode.cs:325-327`, a WPF-specific `TextBlock` content-model quirk) — flagged as a known gap, not resolved this phase (Known gaps).
13. **`PropertyNode.Description`/`IPropertyDescriptionService`, `CreateBinding()`, `NameForeground`(Binding/StaticResource coloring) are dropped entirely** — no such service exists in this port, and binding/resource-value editing is out of scope this phase.
14. **No `BasicMetadata`-style real seeding of `Metadata.AddPopularProperty` for common WinUI controls this phase** — consistent with Phase 4e Decision 6. The Popular bucket may be empty or sparse out of the box; this does not break categorization correctness (everything else still lands correctly in Other/Attached/Special via the namespace-prefix/attached checks, which need no seed data). Deferred as future polish, same status as Phase 4e's own deferred seeding.
15. **No name/type/filter header row, no Events tab, no `GroupMode` switch, no right-click context menu (Reset/CreateBinding)** ported — `PropertyNode.Reset()`/`CanReset` remain as plain methods a future context menu could call, but no menu is built this phase. (Reference's own alternate `GroupByCategorys`/`Ungrouped` modes are already commented out and dead in its own XAML — only `GroupByPopularCategorys`, i.e. the 4-bucket scheme, is live.)
16. **Selection feed**: `PropertyGridControl.SelectedItems` is a plain settable property, not bound to `ISelectionService` internally — mirrors the reference's own `PropertyGridView.SelectedItems` (its host XAML does the binding). This port has no shell app yet (Phase 5), so tests set `.SelectedItems` directly, the same pattern `DesignSurfaceTests` and other Designer.Tests use for host-less control testing.

## Architecture

```
WinUIDesigner.DesignModel/PropertyGrid/
    PropertyNode.cs      — view-model: wraps DesignItemProperty[], Value/DesignerValue/ValueString,
                            IsSet/IsAmbiguous/Reset, Children/MoreChildren drill-down, lazily
                            resolves its Editor via EditorManager.CreateEditor on first Load.
    Category.cs          — plain view-model: Name, Properties (IReadOnlyList<PropertyNode>), IsExpanded.
    EditorManager.cs      — static registry + resolution (Decision 4).

WinUIDesigner.Designer/PropertyGrid/
    PropertyGridControl.cs — Control subclass. Owns 4 Category buckets, SelectedItems, node cache,
                              Reload()/PickCategory()/AddNode() (folded from reference PropertyGrid.cs),
                              builds its visual tree via C# factory methods (no XAML).
    Editors/BoolEditor.cs
    Editors/ComboBoxEditor.cs
    Editors/NumberEditor.cs
    Editors/TextBoxEditor.cs
```

`DesignItemProperty.cs` (existing file) gains one new virtual member (Decision 1). `XamlModelProperty.cs` (existing file) gains one override.

## Data flow

1. Host sets `PropertyGridControl.SelectedItems = new[] { designItem, ... }`.
2. `Reload()`: clears visibility flags on existing nodes/categories (not discarded — cache reused across reloads, matching reference's `nodeFromDescriptor` caching, keyed by property name string here); if 1 item selected, `IComponentPropertyService.GetAvailableProperties(item)`; if >1, `GetCommonAvailableProperties(items)`.
3. For each descriptor: build/reuse a `PropertyNode` wrapping `DesignItemProperty[]` (one per selected item, via `item.Properties.GetProperty(descriptor.Name)`); skip if `!Metadata.IsBrowsable(node.FirstProperty)`; bucket via `PickCategory` (Decision 7) into one of the 4 `Category`s, sorted by name.
4. `PropertyNode.Load(...)` resolves `Editor` once via `EditorManager.CreateEditor(FirstProperty)` (Decision 4) and wires `ValueChanged`/`ValueOnInstanceChanged` for live refresh.
5. `PropertyGridControl` builds/updates its visual tree: one row per visible `Category` (name + expand toggle + its `Properties`), one row per visible `PropertyNode` (name, using Decision 2's qualified form for attached properties + `Editor` as content).
6. Editing: the editor control's own change event calls `property.SetValue(newValue)` (or, for the whole node across multi-select, `PropertyNode.DesignerValue = newValue` which loops `SetValue` across `Properties`) — routes through `UndoService` automatically, no `ChangeGroup` needed (verified above).
7. `Reset()`: `PropertyNode.Reset()` calls `.Reset()` on each wrapped `DesignItemProperty` — same undo path.

## Known gaps

- **`NumberBox`/`ComboBox`/`CheckBox`/`TextBox` WinUI availability and the exact properties this phase needs are assumed, not yet empirically probed** in this codebase — the task touching each editor should confirm via a real build+test before relying on it further, per this project's established discipline.
- **WinUI value-type `TypeConverter` coverage beyond `bool`/numeric/`enum`/`string`** (e.g. whether `Microsoft.UI.Xaml.Thickness`/`CornerRadius`/`Brush` carry the same converters WPF's equivalents do) is unverified — irrelevant to this phase's MVP editor set, but any future phase adding more editors must check per type, not assume.
- **`TextBlock.Text`-vs-`Inlines` special case** (Decision 12) not ported — editing `TextBlock.Text` through the generic `TextBoxEditor` while the element also has `Inlines` content set could leave stale `Inlines` content in rare cases. Not resolved this phase.
- **No `BasicMetadata`-style real seeding** (Decision 14) — Popular bucket may be sparse/empty until a future phase seeds it.
- **Attribute-driven per-property/per-type editor override mechanism** (`[PropertyEditorAttribute]`/`[TypeEditorAttribute]`) not ported at all, not even as an unconsumed seam (Decision 8) — a genuine YAGNI cut, revisit only if a real future need appears.

## Out of scope

Name/type/filter header row, Events tab, right-click context menu (Reset/CreateBinding UI — the underlying methods exist), `GroupMode` switch, Brush/Color/Collection/TimeSpan/Event/RichText editors, `BasicMetadata` seeding, shell-app wiring (no shell exists yet — Phase 5), OutlineView (Phase 4g, not started).
