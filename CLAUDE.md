# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A port of SharpDevelop's `WpfDesign` (a runtime WYSIWYG XAML designer engine) from WPF to **WinUI 3**. Read-only reference source for the port lives at `F:\ReferencesCode\CSharp\WpfDesigner` — never edit it, only read from it. The port is being built in five sequential phases (XamlDom → DesignModel core engine → DesignPanel/DesignSurface → concrete design-time behaviors → shell app); phases 1–4b are done. Each phase has a spec and a plan under `docs/superpowers/specs/` and `docs/superpowers/plans/` — read the relevant one for exact rationale, verified WinUI API facts, and file:line history before making non-trivial changes in an area you haven't touched before.

`src/` contains exactly one `.xaml` file: `src/WinUIDesigner.Shell.App/App.xaml`. That is not a
style choice. A WinUI 3 project containing no compiled XAML produces no app-level merged
`resources.pri`, so `ms-appx:///` cannot be resolved, `XamlControlsResources` fails to load
`themeresources.xaml`, and every control whose default template references a theme brush
fail-fasts the process with `0xC0000409` during the first layout pass. All other shell UI is
written in C#, like `OutlineViewControl` and `PropertyGridControl`. Do not add a second
`.xaml` file, and do not add a hand-written `app.manifest` — it replaces the generated
registration-free WinRT activation manifest and the app will not start.

## Build

```
dotnet build WinUIDesigner.sln
```

Target framework for every project: `net10.0-windows10.0.19041.0`, `UseWinUI=true`, `Microsoft.WindowsAppSDK` pinned to `1.7.250606001` (do not bump silently — treat a version change as its own decision). `Nullable` is `disable` throughout, matching every prior phase. `RuntimeIdentifier` is `win-x64`, `SelfContained=false` for the src projects.

## Test

**Tests must be run via each test project's built `.exe`, not `dotnet test`.** `Microsoft.UI.Xaml` objects are WinRT classes with thread affinity that can only activate on a thread running inside `Microsoft.UI.Xaml.Application.Start`, inside a process carrying WinUI's registration-free activation manifest. That manifest is embedded into each test project's own apphost at build time (`OutputType=Exe` + NUnitLite, see each project's `Program.cs`) — `dotnet test`'s `testhost.exe` ships with its own pre-built manifest and cannot activate `Microsoft.UI.Xaml` classes at all. Under `dotnet test`, every test needing a live WinUI object reports **ignored** (not failed, not passed) — large "Skipped" counts from `dotnet test` are not a green run.

```
dotnet build WinUIDesigner.sln

tests/WinUIDesigner.XamlDom.Tests/bin/Debug/net10.0-windows10.0.19041.0/win-x64/WinUIDesigner.XamlDom.Tests.exe --noresult
tests/WinUIDesigner.DesignModel.Tests/bin/Debug/net10.0-windows10.0.19041.0/win-x64/WinUIDesigner.DesignModel.Tests.exe --noresult
tests/WinUIDesigner.Designer.Tests/bin/Debug/net10.0-windows10.0.19041.0/win-x64/WinUIDesigner.Designer.Tests.exe --noresult
tests/WinUIDesigner.Shell.Tests/bin/Debug/net10.0-windows10.0.19041.0/win-x64/WinUIDesigner.Shell.Tests.exe --noresult
```

Run a single test with NUnitLite's own filter flag, e.g. `... .exe --test=WinUIDesigner.Designer.Tests.MoveTests.SomeMethod`. `dotnet test WinUIDesigner.sln --filter <Name>` still works for IDE discovery and for the subset of tests that touch no live WinUI object, but treat it as a supplement, never a replacement for the `.exe` run.

`WinUITestHost.RunOnWindow(...)` is `RunWithWindow` without the trailing `Content = null`, for a fixture that builds one tree in its setup and drives that same live tree across several tests; its caller owns the cleanup.

Two reporting artifacts of running test bodies on the shared dispatcher thread, both measured, neither a real failure: an assertion that fails inside `WinUITestHost.Run` is listed **twice** — once against the test that actually failed and once against a different test in the same fixture — so read the stack trace, which names the real one, rather than the count. And `Console.WriteLine` from inside a `Run` body only reaches the output of the *first* test in a process to start the dispatcher thread; later tests' output vanishes. Write diagnostics to a file, or run one test per process, when it matters.

`tests/WinUIDesigner.TestHost` is shared test infrastructure (not a test project itself): `WinUITestHost.Run(...)`/`RunWithWindow(...)` marshal a test body onto the process-wide WinUI dispatcher thread (started lazily, one shared `Window` reused and never closed — closing the last window ends the dispatcher's message loop and kills every later test). `ReflectionXamlMetadataProvider` backs the `TestApplication`'s `IXamlMetadataProvider` so `XamlReader.Load` can resolve test fixture types.

## Architecture

Three layered library projects, each with a `.Tests` counterpart of the same name, plus the shell application that hosts them:

```
WinUIDesigner.XamlDom         — WPF→WinUI XAML DOM: parse/serialize XAML into an object model, no UI.
        ↑
WinUIDesigner.DesignModel     — DesignItem/DesignContext/PlacementOperation/extension framework,
                                 plus a WinUI Adorner replacement (WinUI has no Adorner/AdornerLayer).
        ↑
WinUIDesigner.Designer        — DesignPanel/DesignSurface: live visual-tree hosting, hit-testing,
                                 selection, and the ~56 concrete design-time behaviors (resize/rotate/
                                 skew thumbs, snaplines, per-container placement, drag-move/reparent,
                                 Grid row/column editing).
        ↑
WinUIDesigner.Shell           — the shell app's logic and UI, all in C#: Document, ShellModel,
                                 Toolbox, ShellTypeFinder, ShellMetadata, ToolboxView, MainWindow.
                                 A class library, and deliberately free of XAML.
        ↑
WinUIDesigner.Shell.App       — the executable. Holds App.xaml, App.xaml.cs and Program.cs (an
                                 STA Main; see the runner findings below) and nothing else.
```

`Shell` and `Shell.App` are two projects rather than one for a measured reason: any `ProjectReference`
from a WinUI-hosting test `.exe` to a project carrying an `ApplicationDefinition` fail-fasts that test
host with `0xC0000409` before a single test body runs. Keeping the classes in a XAML-free library lets
`WinUIDesigner.Shell.Tests` reference them the same way the other three test projects reference
`WinUIDesigner.Designer`.

Each project only depends on the ones above it in this list (`ProjectReference`s in the `.csproj`s make this explicit). `tests/WinUIDesigner.TestHost` is referenced by all three `.Tests` projects.

**Extension system** (`WinUIDesigner.DesignModel/Extensions/`): every `DesignItem` gets a set of `Extension`s attached by an `ExtensionServer`, matched by type via `[ExtensionFor]`/`[ExtensionServer]` attributes and resolved through `ExtensionManager`. This is how per-control-type design-time behavior (a resize thumb, a Canvas-specific placement rule, a Grid adorner) gets attached without the core engine knowing about concrete controls.

**Placement chain** (`WinUIDesigner.Designer/Extensions/`): container-specific placement composes as a short `IPlacementBehavior` chain — `DefaultPlacementBehavior` (generic Width/Height resize) → `RasterPlacementBehavior` (snap-to-grid) → `SnaplinePlacementBehavior` (snap-to-sibling-edge) → `CanvasPlacementSupport` / `GridPlacementSupport` (container-specific coordinate systems: `Canvas.Left/Top`, `Grid.Row/Column`). `StackPanelPlacementSupport` bases directly on `DefaultPlacementBehavior` since reordering isn't a coordinate-snapping concern. `PlacementOperation.ChangeContainer` plus `DefaultPlacementBehavior.LeaveContainer`/`EnterContainer` are the reparenting mechanism a `MoveLogic` class drives for cross-container drag-move, triggered by `AdornerProvider` extensions built on the `DragListener` primitive (`PointerPressed`/`PointerMoved`/`PointerCaptureLost`).

**Undo**: every mutation goes through `PlacementOperation`/`ChangeGroup`/`UndoService` so a whole gesture (resize, move, reparent) commits as one undo entry.

## Known WinUI platform gaps (compiler-confirmed absent — do not assume otherwise)

`Rect.Inflate`, the static `Brushes` class, `UIElement.TranslatePoint`, `RowDefinition.Offset`/`ColumnDefinition.Offset`, `CombinedGeometry`/`GeometryCombineMode`, `Animatable`/`Geometry.BeginAnimation`/`RectAnimation`/the 3-arg `DoubleAnimation` constructor, `Visibility.Hidden` (only `Visible`/`Collapsed`), `DispatcherPriority.Loaded` (`DispatcherQueuePriority` has only `Low`/`Normal`/`High`), `InvalidateVisual`, `SolidColorBrush.Freeze()`, `DoubleCollection(IEnumerable<double>)`, single-arg `TextBox.GetRectFromCharacterIndex`, `Canvas.RightProperty`/`Canvas.BottomProperty`, `Microsoft.UI.Xaml.Media.PathSegment.IsStroked`/`.IsSmoothJoin` (WPF-only — `PathSegment` in this WinUI SDK declares no properties of its own at all beyond what it inherits from `DependencyObject`, confirmed by both a `CS1061` compile error and reflecting over the live WinRT type; there is no per-segment stroke/join equivalent anywhere in WinUI's `Path` model), `Microsoft.UI.Xaml.Media.LayoutInformation` (the WPF `LayoutInformation.GetLayoutSlot` static class has no projected equivalent in this WinUI 3 SDK — confirmed by `CS0234`; use `FrameworkElement.ActualOffset`/`.ActualSize` against a live layout pass instead, which reflects post-arrange, pixel-snapped values). `DoubleCollection` also cannot be shared across `Shape` instances at runtime (not a compile error, an empirically-found runtime constraint). `Microsoft.UI.Xaml.Media.PointCollection`'s projected indexer does not bounds-check: `points[i]` for `i >= points.Count` (or negative) returns `Point(0,0)` rather than throwing `ArgumentOutOfRangeException` the way WPF's `PointCollection` would (confirmed empirically on a live object: `count=3` probe at index `99` returned `Point(0,0)`, no exception) — code relying on WPF's throw-on-out-of-range behavior as an implicit assertion will instead silently read a phantom `(0,0)` point. A `FrameworkElement`'s arranged position/size can round to the nearest pixel at the default `RasterizationScale` (e.g. an arrange rect of `(16.5, 26.5, 7, 7)` reads back via `ActualOffset`/`ActualSize` as `(17, 27, 7, 7)`) — symmetric across both axes, not a bug; give coordinate assertions against real layout output a tolerance (0.5px at 1x scale) rather than asserting exact fractional values. Three more found while building the shell (Phase 5), each after a wrong assumption cost real time. **A `ListView` bound through `DisplayMemberPath` against `System.Type` renders every row blank**: `typeof(X)` is an instance of the non-public `System.RuntimeType`, and WinUI's binding engine reflects against an object's actual type, so `"Name"` never resolves — the containers realize with correct sizes and no text, which looks like a layout bug and is not. Bind to a public class of your own (`ControlNode` here) instead. **Never nest a `ListView` inside a `ScrollViewer`**: the list contains its own, and the outer one hands it an infinite available height — measured here as a 200x6360 `ListView` inside a 200x680 parent, with all 159 containers realized against an unbounded viewport. **`System.Windows.Automation` crashes a WinUI 3 app**: walking the tree with `FindAll(TreeScope.Descendants, ...)` killed the process with `0xc0000005` inside `Microsoft.UI.Xaml.dll`, so it is not usable for driving or inspecting this app; `SendKeys` does not reach a XAML island either. Both of those hold, but the walkthrough does **not** need a human: on 2026-09-08 the shell's whole eight-step manual walkthrough was driven end to end from PowerShell. What works and what does not was measured. **UIA kills the app from outside the process too, not just from inside**: an out-of-process `System.Windows.Automation` client walking `TreeScope.Descendants` returned 0 elements and the app died; walking one `TreeScope.Children` level at a time returned only a 1424x720 `Pane` containing a 0x0 `Pane`, and the app died ~5s later, against a control run that sat idle for 90s and lived. So UIA cannot locate anything in this app and cannot be used to drive it. **`SendInput` is accepted and silently dropped** — it returns 1 with the cursor unmoved, for both mouse and keyboard. **The legacy trio does work**: `SetCursorPos` + `mouse_event` (`0x0002`/`0x0004`) for clicks and `keybd_event` (with `VkKeyScan` for characters) for typing reach the XAML island, the app's `MenuBar` flyouts, and Win32 file dialogs, including accelerators like Ctrl+O and Ctrl+S. Since elements cannot be located, coordinates have to come from a screenshot: capture the window's **client** rect via `GetClientRect` + `ClientToScreen` + `Graphics.CopyFromScreen`, and image pixels then equal the client coordinates a click takes. Menu flyouts and file dialogs are separate top-level HWNDs, so they need a whole-virtual-screen capture instead. Two traps: a `MenuFlyoutItem` sometimes takes the first click as hover only and needs a second click at the same point, and the mode bar's y-coordinate moves by ~40px depending on whether the error strip is showing. Three more were measured while making the shell's `MainWindow` testable in-process, and they bound what that is able to prove. **A test process cannot load `XamlControlsResources`**: with no compiled XAML there is no merged `resources.pri`, `ms-appx:///` does not resolve, and constructing it throws `COMException` 0x80004005. Controls whose default style lives only in that dictionary are then unusable - `MenuBar` measures to zero, `TextBox` and `NumberBox` fail their first layout pass with a bare `E_FAIL`. `MenuBar` at least names the keys it wants (`TabViewButtonBackground`, `TabViewScrollButtonBackground`) in the exception's `Data["RestrictedDescription"]`, never in its `Message`, so seeding them by hand works; `TextBox` names nothing and cannot be seeded around. **A second live `Window` in a test process is fine in general but not with a `TextBox` in it**: `ListView`, `ToolboxView`, `OutlineViewControl`, `DesignSurface` and `ScrollViewer` were each measured going live in one, while a lone `TextBox` fail-fasts the host with `0xC000027B` (STOWED_EXCEPTION) during the first layout pass. Since the host's own shared window handles a `TextBox` normally, a window-owning test and a `TextBox`-using test are mutually exclusive in one process - which is why `MainWindowInteractionTests` hosts the shell tree in the shared window and marks its focus-guard test `[Explicit]`. **Ruling 6 holds for a project's own `ApplicationDefinition`, not just a referenced one**: adding an `App.xaml` to a test project (with `DISABLE_XAML_GENERATED_MAIN`) does generate the merged PRI, and still fail-fasts the host before a single test body runs. **Constructing any `DependencyObject` permanently commits native memory that is never returned** — about 430 bytes for a `SolidColorBrush`, 900 for a `Border` or `Grid`, 1,500 for a `Button`, measured by looping construction-and-drop with nothing else running. A plain WinRT runtime class (`Windows.Foundation.Collections.ValueSet`) costs nothing, so this is the XAML core, not CsWinRT. It does not plateau (5,000 iterations of ten `Border`s held a 15.5–17.6 KB/iteration slope from 37 MB to 113 MB), it is not affected by pumping the dispatcher between iterations, it is not affected by whether a live `Window` exists to render frames, and nothing is rooted on the managed side (20 bare `Border`s, 0 alive after a full collect). So **do not write a byte budget for anything in this port** — the floor is the platform's and scales with how many `DependencyObject`s the work touches; count the objects the code builds instead, the way `DocumentObjectBudgetTests` does. Two more were measured while wiring `DocumentView`'s XAML editor (Phase 5, shell document tabs, Task 3). **`TextBox.TextChanged` does not fire for a programmatic assignment in a test process** — confirmed for a detached `TextBox`, for one inside a live tree in the shared window, and even assigning through `SetValue` directly on `TextBox.TextProperty`, in every case with `Text` itself updating correctly. Only real user typing raises it here, so production is unaffected, but anything a test needs to drive on that path has to live behind a method rather than inside the `TextChanged` handler itself. **A `TextBox` nested under a freshly assigned `StackPanel`/`Grid` window content throws a `COMException` on first layout whose `Message` and every `Data` entry are empty**, so nothing can be seeded around it; the same `TextBox` inside a constructed `MainWindow` tree lays out normally, and why is not root-caused.

Four more were measured on 2026-10-25 driving the real app on the GitHub `windows-latest` runner (`.github/workflows/walkthrough.yml`), each invisible to the suites because a test cannot raise a routed pointer event or a real OS drag. **`PointerCaptureLost` is a routed event**: it bubbles, so a handler on an ancestor sees a descendant's capture loss and must check `e.OriginalSource` before treating it as its own. **Over any `Panel`/`Border`/`ContentControl`/`Viewbox` the `PanelMove` overlay's `DragListener` already holds the pointer capture by the time a press reaches `DesignPanel`**, so `DesignPanel.CapturePointer` returns false there; pointer moves and the release still bubble up from the overlay. **`FindElementsInHostCoordinates` skips a `Panel` with a null `Background`**, and a new document's root `Canvas` has none; `DesignPanel.HitTest` now falls back to a bounds pass for such panels, so test fixtures no longer need to set a `Background` to hit one. **The XAML compiler's generated `Main` left the UI thread in the multithreaded apartment** (measured with `CoGetApartmentType`: type 1, managed `ApartmentState.MTA`), and OLE needs a single-threaded one. So every `ListView` item drag fail-fasted the app with `0xC0000409` right after `DragItemsStarting` returned, even with a handler that only called `e.Data.SetText`, and the WinRT clipboard threw `CO_E_NOTINITIALIZED`. It was first blamed on the runner running the app elevated, which was wrong. `src/WinUIDesigner.Shell.App/Program.cs` now supplies `Main` (`DISABLE_XAML_GENERATED_MAIN`) and runs the app on an STA thread. The runner then measured MAINSTA, and a real toolbox drag placed its control; the walkthrough's last steps cover it. **On the runner, keys typed into the `FileOpenPicker` land unpredictably** - over three runs they were lost, went to the address bar after a click on the File name box and after Alt+N, and a file path typed there is refused ("You can't open this location using this program") - while the `FileSavePicker` starts with focus in its File name box and takes typing normally; mouse input reaches both, so the walkthrough saves into Documents (both pickers' start folder) and opens the file by double-clicking its row. `SystemDesignerClipboard` uses the Win32 clipboard API (`OpenClipboard`/`SetClipboardData`). It was written while the WinRT clipboard was failing for the apartment reason above, and calling `OleInitialize` on an MTA thread changes nothing. It is kept because it is synchronous and proven on the runner. An exception thrown from a `KeyboardAccelerator.Invoked` handler shows no unhandled-exception dialog and leaves no trace, so a command that silently does nothing on the real app needs a trace to diagnose, not a guess. The walkthrough's screenshots are published to `refs/walkthrough/latest` because Actions artifacts and log downloads live on a blob host this environment's proxy refuses; `git fetch origin refs/walkthrough/latest` reaches them.

Before assuming a WPF API exists in WinUI, check the spec's "WinUI API surface" section for the phase you're touching, or verify empirically (`dotnet build` against a throwaway probe, or direct `Microsoft.UI.Xaml.winmd` metadata inspection) rather than guessing — this codebase has been burned by wrong assumptions here more than once.

## Working with SharpDevelop-derived files

Files ported from `WpfDesign` (e.g. `ExtensionManager.cs`) carry the original SharpDevelop MIT copyright header — keep it when editing those files. Follow each file's existing brace/indentation style rather than imposing a different one across the codebase; ported files and newly-written files differ slightly in convention.
